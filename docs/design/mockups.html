Inbox (home)

The home screen routes attention — it doesn't monitor activity.

32The unit of work is a decision, not a session

Agents parallelize production; the human is the serial bottleneck. So the home screen is a queue of pending decisions — merge, review, approve, resume — each with its action inline, ranked by decision cost then age (quick confirmations first, stale items flagged). Watching sessions run stays one click away; it's just no longer the default job.

33Auto-approved still means human-merged

Code review's low-risk auto-approval clears the review, not the accountability: merging stays a human click — made a ten-second one. The Merge button re-validates CI, approval state, and RBAC server-side at click time; the rendered queue is never trusted as authority, consistent with the platform's policy-on-the-server invariant.

34Every row says why it's yours

Direct assignment, requested review, or a CODEOWNERS path resolved to a person through the identity graph — the provenance is printed on the row. A queue whose origin you can't trust becomes a queue you ignore; provenance is what makes this an inbox rather than a feed.

Session

The core screen — rendering the typed event stream.

1Statuses that tell the truth

cancelled, failed · timeout, booting, completed — four semantic colors, four meanings. No more "Failed" badge on a session that was merely stopped — the top source of support tickets.

2Boot is a progression, not a spinner

Cold starts can take minutes. Phases and real durations are shown — a slow boot is distinguishable from a dead one.

3Every failure is actionable

Persisted reason (heartbeat_silence, not "something went wrong") and a one-click resume that replays the same conversation on a fresh sandbox — work is never lost, and the UI says so.

4A timeline of typed events

Tool calls collapsed with durations, per-step cost, streaming text. The UI merely renders the generated contracts — thin by construction.

5A composer that pre-warms

Typing triggers sandbox warm-up ("0s to dispatch"). Plan mode, model and effort are first-class — no more scattered state, the source of the repeated plan-mode regressions.

6"What happened?" as self-service

Timestamped state transitions, generation, runtime fingerprint, correlation id — everything you'd otherwise dig out of the server logs, self-service.

31The source stays attached to the session

A session started from Slack, Linear, or a GitHub mention carries that origin through its entire lifecycle — it's what tells the outbox which thread, activity, or comment to deliver the completion notification to. A session opened directly in the web app has no callback channel; showing that plainly is itself useful, not just decorative.

Code review

The verdict as an editable object; policy enforced on the server.

7The verdict is a risk map, not a wall of text

Risk areas × severity × assessment, editable by maintainers, labels kept in sync. The "posted via server-side verdict tool" badge makes the invariant visible: the severity floor is enforced by the server, never by the prompt.

8Sentinels report their own status

Coverage, doc-drift, visual-QA: each sentinel reports pass/fail/skipped separately from the verdict — you see what was checked, not just the conclusion.

9Suggestions apply through a validated endpoint

"Apply suggestion" goes through the server (the agent never posts raw comments), and "Dismiss with rebuttal" feeds reconciliation: a rebutted finding is not re-raised on re-review.

10One PR = one session

Concurrent @mentions are coalesced (atomic claim) and the session is reused — the rail shows it instead of hiding it, with the history of successive reviews.

11Handoff-readiness runs only on scoped sessions

A PR from a path-scoped Environment gets an extra check: which called endpoints have no entry in contracts/api/*, and what backend TODOs the agent left behind. It never blocks or re-litigates the PR's own risk verdict — it exists so an engineer picks up exactly what's missing, not the whole diff.

Release review

Reviewing a release is a different job from reviewing a PR — same components, a different lens.

12The manifest is an audit, not a verdict

Every constituent PR's review and CI status is checked at its merge commit, not the latest one — a force-push after approval can hide a run that was red when it actually merged. Admin overrides and unreviewed reverts are flagged the same way. No code-reasoning involved: this is compliance, mechanized.

13The aggregate pass only runs when it's likely to matter

Re-reviewing already-approved code on every release doesn't scale. The trigger is shown, not hidden: here, three PRs touched the same subsystem — that's the actual signal, not an arbitrary release-day ritual.

14A different lens: composition, not correctness

Findings here are about how already-correct changes interact — a stale test fixture, a shadowed migration — never a re-litigation of logic already approved per PR. Both examples mirror concrete failure classes (a migration-numbering collision, a rename regressed by an unrelated merge) that no single PR's review could have caught.

Plan mode

The plan is an artifact; approval is multi-channel.

15The plan is persistent and versioned

A structured document (steps, scope, v1→v2 history), not a message scrolling away. Comments produce a new version; approval targets a specific version.

16Server-side dispatch on approval

"Approve & build" triggers the implementation turn server-side — a verdict given in Slack or Linear has exactly the same effect; first one wins, the other channels are notified.

17Plan model ≠ build model

The split (Opus to plan, Sonnet to build) is shown in the header, not buried in a setting — a feature that regressed twice for lack of visibility.

Automations

Health before detail.

18Health is a column, not an investigation

Success ratio, strikes before auto-pause ("2/3"), auto-paused state with one-click resume. Silent auto-pause becomes impossible to miss.

19Invocation → runs, the fan-out made explicit

Each invocation lists its per-target runs with a typed failure reason (image_build_failed) and a link to the session — no more "it didn't run" with no trail.

20The result readable without opening the session

artifact_summary as the first line of every run: what the automation produced, in one sentence. A classic gap: the column exists in the UI but the backend never fills it.

Settings

Configuration stops being a source of incidents.

21Path-scoped Environments, enforced by sparse-checkout

A product-prototyping Environment restricts a session to specific paths — enforced at the git layer (sparse-checkout), so backend code is physically absent from the sandbox, not merely off-limits by convention. The paired mock service, declared like any other services.yml entry, means the prototype still runs end-to-end.

22Secrets show their resolution

The automation → environment → repo → global order is displayed, and each value says who wins for a given target. No more "why isn't my AWS key there" — automations once ran without their sandbox settings for weeks with nothing showing it.

23Image builds are observable

Fingerprint, build duration, visible backoff ("retry in 2 h ×4"), and the fallback behavior spelled out ("sessions fall back to base image"). Rebuilds once failed silently for 20 hours straight — here failure is a displayed state, not a buried log.

24Prompts are tuned in production

Versioned classifier templates, editable, with assembled-prompt preview and a quantified shadow mode ("divergence 3.1% over 7 d") before activation — the iteration pipeline, promoted into the UI.

Analytics

Measure what used to hurt.

25False failures as a first-class metric

"Watchdog kills later proven alive" must stay at zero — the health KPI of the new liveness model. Left unmeasured, this share of "failures" is invisible and significant.

26Cost, by model and by session

A schema bug once showed $0 cost across the entire platform for days. Cost becomes a dashboard again: per model, per session (median), and the plan/build split justified by numbers.

27Review quality is measured

Accepted / rebutted / dismissed: the finding acceptance rate drives the tuning of the precision-first review. The "My sessions / All" scope applies here as everywhere. Typed failure reasons link to their sessions.

Sign-in & access

One person, one identity — whatever the channel; policy on the server.

28GitHub sign-in, SSO pluggable

GitHub OAuth is the primary login and doubles as the token used to attribute PRs to the real author. Session cookies are backend-issued and host-scoped — the random-logout incident was another app's cookie colliding on the parent domain. The domain/org allowlist gates signup.

29Identities link themselves

On first contact from Slack or Linear, the platform matches the verified email and auto-links the identity; if the match is ambiguous, it sends an in-channel link prompt — it never guesses. Provider email-API failures are retried and keep the last known value: a GitHub emails outage once nulled identities and broke both sign-in and the Slack↔web link.

30RBAC enforced server-side

Four roles — admin, maintainer, member, viewer — checked by the same policy whatever the channel: a plan approval from Slack passes exactly the same authorization as one from the web. Viewers can watch but never prompt or become PR reviewers (a real past bug), and every state change lands in an audit log carrying the correlation id.

Technical target: Vite + React SPA on types generated from /contracts, served via go:embed from the control-plane binary — self-host install is one binary + Postgres. Static mockups: interactions are indicative. Remaining views to design: session share page, self-host onboarding.
